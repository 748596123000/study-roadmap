Part 01 · 协议基础

协议的三要素

所有协议都在回答同一个问题：双方按什么规则说话。规则由语法、语义、时序三部分拼成。

Part 01协议基础
先把「协议」这个词定义清楚，后面每个协议才好归位。

Fundamentals · 协议基础

协议 = 语法 + 语义 + 时序

协议不是「一句话约定」，而是一份双方都要实现的规则集。少对齐任何一项，通信都会出问题。

语法 · Syntax

消息长什么样：字段名、类型、编码方式、字节序。

{"jsonrpc": "2.0", "method": "search", "id": 1}
语义 · Semantics

每个取值代表什么：状态码含义、错误码归类、字段的约束条件。

-32601 = 方法不存在 -32602 = 参数非法 200 + errBody = 语义错位
时序 · Timing

谁先谁后：请求顺序、超时时长、重试次数、并发与背压。

connect → handshake → request → stream timeout 30s / retry ×2
最容易踩的坑

语法对齐 ≠ 通信正确。两边字段名一模一样，但错误码含义不同、或者 200 里面装着错误内容——这类「静默失败」比直接报错难查十倍。对接时先对齐语义表，再对齐字段表。

Part 01 · 协议基础协议三要素
强调语义层是最容易漏的。AI 开发场景里尤其常见：接口返回 HTTP 200，body 里是 {"error": "..."}，客户端没判断就当成功处理。

关键修正

gRPC 不是独立的一层：它 = Protobuf 序列化 + HTTP/2 传输 + gRPC 调用约定。JSON-RPC 是传输无关的规范，实际多跑在 HTTP 或 WebSocket 上。WebSocket 也不是应用层协议——它是 HTTP 升级而来的传输层协议。

Part 02 · 传输与流式

字节怎么流动

HTTP、WebSocket、SSE 三者的差别，最终都落在「谁来发起、连接怎么建、断了怎么办」这三个问题上。

Part 02传输与流式
进入具体协议。先对比 HTTP 与 WebSocket，再讲 SSE 和调用约定。

Transport · 传输层

HTTP 与 WebSocket：一次性 vs 持续性

📨HTTP / HTTP2

请求 → 响应，一问一答

  • 无状态：会话靠 Header / Cookie 维持，不在连接里
  • 连接复用：HTTP/1.1 keep-alive；HTTP/2 多路复用 + HPACK 头部压缩 + 二进制帧
  • 流式响应：HTTP/1.1 用 chunked 编码，HTTP/2 用 DATA 帧
  • 服务端推送已弃用（HTTP/2 Server Push），推流改用 SSE 或 WebSocket
  • 生态成熟：网关、缓存、鉴权、限流全都现成

🔗WebSocket

握手后转独立帧协议，全双工

  • 握手：GET /ws + Upgrade: websocket + Sec-WebSocket-Key → 101 Switching Protocols
  • 帧结构：FIN / RSV / opcode（text·binary·close·ping·pong）/ mask / payload length——不再是 HTTP 报文
  • 心跳：ping / pong 帧探测半开连接，穿越 NAT 与代理超时的必备机制
  • 断线重连：协议不提供，须自行实现指数退避 + 会话续传
  • 典型场景：IM、协同编辑、实时语音、行情推送
怎么选

只要「服务端单方面推给客户端」，用 SSE 更轻——它就是普通 HTTP，不需要额外握手和心跳；需要双向实时（客户端也要高频上行）才上 WebSocket。HTTP 与 WebSocket 也能共存于同一服务，靠路径区分。

Part 02 · 传输与流式HTTP vs WebSocket
原图对 WebSocket 的描述停留在「实时推送」四个字，缺了握手、帧、心跳、重连这四个真正决定工程实现的机制。

Streaming · 流式传输

SSE：把单向流塞进普通 HTTP

📡机制

Content-Type: text/event-stream

  • 服务端不关闭响应体，持续追加事件帧；每帧以空行结束
  • 可选字段：data / event / id / retry
  • 浏览器原生 EventSource：自动重连，并用 Last-Event-ID 续传，服务端可据此补发
  • 局限：单向（上行需另开 HTTP）；HTTP/1.1 下同域并发连接约 6 条，需关代理缓冲（X-Accel-Buffering: no）
HTTP/1.1 200 OK Content-Type: text/event-stream data: {"type":"token","v":"你"} data: {"type":"done"}

🔍层次澄清（重要）

原图把 SSE 与「向量化 / 检索」画成了同一层的流水线

应用模式
RAG（向量化 / 检索 / 重排）发生在服务端内部，是一次检索 + 一次生成的组合算法。
传输方式
SSE只负责「把服务端产出的内容增量推给客户端」，它不关心内容从哪来。
正确关系
RAG 在服务端算完 → 结果通过 SSE 推给前端。二者是上下层，不是并列步骤。
工程现实
OpenAI / Anthropic 的流式 chat completion 接口用的就是 SSE；工具调用回合同样是 SSE 上的一段 JSON。
对比

轮询：反复建请求，浪费且延迟高；长轮询：服务端挂起连接，仍需自己重连；SSE：纯 HTTP 语义 + 浏览器自带重连，是 AI 流式输出的事实标准。

RPC · 调用约定

JSON-RPC / gRPC：让接口不再靠口口相传

🧬JSON-RPC 2.0

规范本身与传输无关，最常跑在 HTTP 或 WebSocket 上

// 请求 {"jsonrpc": "2.0", "method": "search_docs", "params": {"q": "向量检索"}, "id": 1} // 成功响应 {"jsonrpc": "2.0", "result": {"hits": 3}, "id": 1} // 错误响应 {"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 1}
  • id 关联请求与响应；无 id 即 notification，服务端不回复
  • 批量请求：传 JSON 数组，服务端返回结果数组
  • 保留错误码：-32700 解析失败 / -32600 请求无效 / -32601 方法不存在 / -32602 参数非法 / -32603 内部错误

🧱gRPC

schema 先行，双端生成桩代码

  • .proto 定义 service / method / 消息类型 → protoc 生成各语言客户端与服务端代码，签名不可能漂移
  • Protobuf 二进制编码，体积小、解析快
  • 跑在 HTTP/2 上，四种调用模式：unary / server-streaming / client-streaming / bidirectional
  • 代价：浏览器原生不支持，需 gRPC-Web 或代理；调试不如 JSON 直观
措辞修正

原图说「像调本地一样」——准确说法是「像调函数一样」。它仍是远程调用：有序列化开销、有网络延迟、可能部分失败。因此必须配套超时、幂等键、重试与熔断。

MCP · AI 接入标准

MCP：把「AI 接外部世界」标准化

Anthropic 提出并开源，现由 Linux Foundation 旗下 Agentic AI Foundation（Anthropic、Block、OpenAI 共同发起）托管，走中立治理。

🔧 Tools

模型可调用的动作，通常有副作用（写库、发消息、扣款）。执行前一般需用户确认。

search · create · execute

📚 Resources

可读取的上下文数据，通常只读，按 URI 寻址。模型据此「知道」有什么可查。

file:// · db://schema

💡 Prompts

用户显式触发的模板化工作流，不由模型自行决定使用。

/code-review · /summarize

🧩架构：Host / Client / Server

Host 为每个 Server 建立一个专属 Client，严格 1 : 1

  • Host：Claude Code、Claude Desktop、IDE 等 AI 应用，持有对话与权限
  • Client：Host 内部的协议实现，一个 Client 只服务一个 Server
  • Server：暴露 tools / resources / prompts 的独立程序
  • 隐私边界：Server 看不到完整对话，只看到本次请求——权限最小化的关键

🔌承载与定位

JSON-RPC 2.0 消息，两种标准传输

  • stdio：本地子进程，读写标准输入输出，本地工具零端口暴露
  • Streamable HTTP：单一端点 POST，响应可为一个 JSON 对象或请求级 SSE 流
  • 修正：MCP 不等于「云服务接口」——它与「云」无关，本地进程同样是 Server，stdio 才是本地场景的主力
  • 价值在于标准化与可发现：同一份 Server 换个 Host 就能用
